# v1.1.10

修复命令入口可能读取另一套 VSM 配置的执行链缺陷，并保护更改安装根目录时仍在使用的全局版本。

## 修复与改进

- **入口绑定所属配置目录**：旧入口只转发到 CLI，继续使用调用者继承的 `VSM_HOME`。当 GUI 在目录 A 保存 Java 17，而原 cmd 继承目录 B、B 选择 Java 21 时，即使命中 A 的入口，也可能运行 Java 21。Windows/POSIX 入口现在在子进程中绑定所属目录，保留原终端变量及其它目录的默认配置。
- **执行验证检查配置归属**：旧验证强制传入正确目录，可能让上述旧入口误通过。现在使用独立空目录验证继承环境，要求入口仍实际运行所属配置中的版本；日志新增 `owner_home_verified`。
- **安装目录切换保护**：GUI 与 CLI 共用检查；目标目录缺少当前可用全局版本时拒绝更改，保留原配置和文件。目标已准备对应版本时允许切换，旧版已产生的失效查找目录仍可恢复到有效目录。更改查找目录不会自动搬迁已有工具。
- **准确区分版本缺失**：提示和复制诊断显示要求版本、配置来源、当前查找根目录及可见版本，不再把缺少安装归类为程序执行失败。此时提供安装/纳管或恢复目录的建议，并收起无助于补齐安装的 cmd 激活指引。
- **默认目录恢复**：CLI `vsm install-root default` 正确报告恢复后的目录；本地与 Docker 隔离项目均不允许更改全局根目录。

## 更新

```bash
vsm update --gui
```

也可使用 GUI「检查 VSM 更新」。Windows 同时更新 CLI 和 GUI；macOS 应用内置 CLI。

**升级并重启 GUI 后，点击一次「激活 PATH」重建入口。**已经通过 VSM 入口的终端，后续切换无需反复激活。原 cmd 从未加载 VSM 时，按界面提供的命令加载一次。若 `where java` 仍先找到系统 Java，需先让这个终端采用 VSM 入口；本版不会直接改写其它运行中进程的 PATH。

直接调用 CLI 可执行文件仍按其环境读取 `VSM_HOME`；项目版本与 `VSM_JAVA_VERSION` 的优先级保持原规则。

若提示当前安装目录没有所需版本，应恢复实际包含原版本的安装根目录，或在新目录准备对应版本。单纯加载初始化脚本不能补齐缺失安装。目录切换和恢复均保留原文件。

仍有问题时，在原终端运行 `vsm logs diagnose java`，再从 GUI「日志 → 导出」或 `vsm logs export <新文件.jsonl>` 导出。详见[已有运行时与诊断说明](https://github.com/hquip/Vaelen/blob/v1.1.10/docs/system-runtimes.md)。

## 验证

先用真实 CLI 和独立 Java 程序复现“命中 A 入口却运行 B 的 Java 21”，以及“旧验证误通过”，再验证修复。同一 cmd 在延迟展开 ON/OFF 下连续完成 Java 17 → 21 → 17 切换，原终端变量和 B 的默认版本保持不变。回归覆盖特殊路径、退出码 42、POSIX 入口、已有批处理启动命令、安装目录保护与恢复、版本缺失诊断和界面复制。本地完整 race、`go vet` 与三平台 CI 检查 CLI/GUI、数据库和 macOS 实际启动。

这些是已复现的源码缺陷；已有用户的相似症状仍可能由其它配置或命令优先级触发，不能仅凭旧截图断定根因相同。
